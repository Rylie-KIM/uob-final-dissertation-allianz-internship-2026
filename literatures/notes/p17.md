## 🇰🇷 한국어 요약

### 1. 문제 정의 — 기술적 부채로서의 ML 시스템

소프트웨어 공학에서 **기술적 부채(technical debt)**는 빠른 개발을 위해 선택한 단기적 지름길이 장기적으로 유지보수 비용으로 돌아오는 현상이다. 이 논문은 ML 시스템이 전통 소프트웨어보다 훨씬 더 심각한 기술 부채를 축적하기 쉽다고 주장한다.

**핵심 통찰 (§1, Figure 1):** 실제 프로덕션 ML 시스템에서 순수 ML 코드(모델 학습/예측)는 전체 코드의 아주 작은 부분에 불과하다. 나머지는 데이터 수집, 특성 추출, 분석 도구, 설정 관리, 서빙 인프라 등 "배관(plumbing)" 코드다. **기술 부채는 이 주변 시스템 수준에서 발생한다.**

### 2. 핵심 기술 분류 체계

#### 2-1. 경계 침식 (§2 — Boundary Erosion)

**CACE 원칙 (Changing Anything Changes Everything):**

ML 시스템에서 어떤 입력 신호 $x_1, \ldots, x_n$를 사용하는 모델이 있을 때, $x_1$을 변경하면 나머지 $n-1$개의 특성의 중요도, 가중치, 사용 방식이 **모두** 변할 수 있다. 이것은:
- 완전 재훈련(full retrain) 시에도 발생
- 온라인 방식(online learning)에서도 발생

**수정 폭포(Correction Cascades):** 문제 $A$에 대한 모델 $m_a$가 있을 때, 약간 다른 문제 $A'$에 대해 $m_a$를 입력으로 받는 보정 모델 $m'_a$를 만드는 것이 편리해 보인다. 그러나 이것은 $m_a$에 대한 새로운 시스템 의존성을 생성하고, $m_a$의 어떤 변경도 전체 스택에 파급 효과를 가진다.

**미신고 소비자(Undeclared Consumers):** 모델 $m_a$의 출력이 런타임에 공개적으로 접근 가능하면, 다른 시스템들이 명시적 선언 없이 $m_a$의 출력을 소비할 수 있다. 이것이 **숨겨진 피드백 루프(hidden feedback loops)**의 핵심 원인이 된다 (§4로 직접 연결).

#### 2-2. 데이터 의존성 부채 (§3 — Data Dependency Debt)

| 부채 유형 | 설명 | Allianz 관련성 |
|----------|------|--------------|
| **불안정한 데이터 의존성** | 입력 신호가 시간에 따라 질적/양적으로 변화. 특히 다른 ML 모델의 출력을 입력으로 쓸 때 발생 | `model_v1_score`를 `model_v2`의 피처로 사용하면 v1이 변경될 때 v2 전체 동작이 바뀜 |
| **미활용 데이터 의존성** | 레거시 피처, 번들 피처, $\varepsilon$-피처, 상관 피처 등이 모델에 남아 있음 | `postcode_risk` 등 오래된 피처가 사기 패턴 변화를 반영 못할 수 있음 |

정적 데이터 의존성 분석이 필요하다 — 컴파일러가 코드 의존성을 분석하듯, ML 파이프라인의 데이터 의존성을 자동 추적해야 한다.

#### 2-3. 피드백 루프 (§4 — Feedback Loops) — SFP 연구의 핵심

이 절이 dissertation의 직접적인 이론적 근거다.

**직접 피드백 루프 (Direct Feedback Loops):**
> "A model may directly influence the selection of its own future training data."

이것이 Allianz SFP 루프의 정확한 정의다. 모델 $f_\theta$가:
1. 클레임 점수를 생성 → 조사 결정을 구동
2. 조사된 클레임에서만 사기 라벨 관측
3. 이 편향된 데이터로 $f_{\theta'}$ 재훈련

수식으로: 모델 출력 $f(x)$가 미래 학습 데이터 $D_{t+1}$을 생성하는 어떤 과정에 입력되면:
$$D_{t+1} = g(D_t, f_t)$$

이것이 **숨겨진 피드백 루프(hidden data dependency loop)**다.

논문이 제안하는 부분적 완화: (1) **밴딧 알고리즘(bandit algorithms)** 사용 (단, 액션 공간이 클 때 확장성 문제), (2) **일부 무작위화(randomisation)**로 편향 완화.

**숨겨진 피드백 루프 (Hidden Feedback Loops):**
두 시스템이 세상을 통해 **간접적으로** 서로 영향을 줄 때 발생. 두 시스템이 완전히 분리된 것처럼 보여도 실제로는 결합되어 있다.

예시: 상품 추천 시스템과 리뷰 선택 시스템이 각각 독립적으로 운영되지만, 사용자가 더 많이 클릭하는 상품 → 더 많은 리뷰가 쌓임 → 리뷰 시스템의 학습 데이터 변화.

**Allianz 보험 맥락에서의 숨겨진 피드백 루프:**
- 사기 모델 → 조사 우선순위 → 조사관 전문성 개발 → 조사 품질 변화 → 미래 사기 발견 확률 변화
- 사기 모델 → 적립금 설정(reserve setting) → 클레임 조기 종결 결정 → 사기 발견 기회 감소

#### 2-4. ML 시스템 안티패턴 (§5 — ML System Anti-Patterns)

| 안티패턴 | 설명 | Allianz 파이프라인 위험 |
|---------|------|----------------------|
| **글루 코드(Glue Code)** | 범용 패키지를 연결하는 대규모 지원 코드. 시스템을 특정 패키지에 고착 | DoWhy, econml, LightGBM 통합 시 발생 가능 |
| **파이프라인 정글(Pipeline Jungles)** | 데이터 준비 파이프라인이 스크래핑, 조인, 샘플링 단계의 정글로 변함 | `generate_synthetic.py` → `loop_detector.py` → `unbiased_eval.py` 체인 |
| **죽은 실험 코드(Dead Experimental Codepaths)** | 실험적 분기가 메인 코드에 남아 기술 부채로 쌓임 | Knight Capital $4.65억 손실 사례 언급 |
| **추상화 부채(Abstraction Debt)** | ML 시스템을 위한 적절한 추상화가 없음 | "스트림, 모델, 예측의 올바른 인터페이스는 무엇인가?" |

#### 2-5. 설정 부채 (§6 — Configuration Debt)

설정 관리가 코드 못지않게 중요하다:
- 피처 A가 9/14~9/17 사이에 잘못 로깅됨
- 피처 B가 10/7 이전 데이터에는 없음
- 피처 C의 계산 코드가 11/1 전후로 변경됨

이런 설정 이력이 문서화되지 않으면 모델 재현성이 불가능하다.

#### 2-6. 외부 세계의 변화 대응 (§7 — Dealing with Changes in the External World)

ML 시스템은 실세계와 직접 상호작용하고, 실세계는 안정적이지 않다. 모니터링 체계가 필요한 세 가지:

- **예측 편향(Prediction Bias):** 정상 시스템에서는 예측 라벨 분포 ≈ 관측 라벨 분포. 이 차이가 커지면 경보.
- **액션 한계(Action Limits):** 스팸 처리나 경매 시스템처럼 액션을 취하는 시스템은 안전망으로 액션 한계를 설정.
- **업스트림 생산자 모니터링:** 데이터 공급 시스템의 SLA가 ML 시스템의 정확도에 직접 영향.

```python
# §4 기반 SFP 감사 함수

def audit_feedback_loop(df, model_version_cols, 
                         investigation_col, label_col):
    """
    직접 피드백 루프 존재 여부 감사.
    D_{t+1} = g(D_t, f_t) 패턴 확인.
    
    Returns:
        dict with feedback loop indicators
    """
    results = {}
    
    # 1. 모델 점수가 조사 결정을 구동하는가?
    # P(investigated=1 | model_score > threshold) vs base rate
    for col in model_version_cols:
        threshold = df[col].quantile(0.75)
        high_score_inv_rate = df[df[col] > threshold][investigation_col].mean()
        overall_inv_rate = df[investigation_col].mean()
        results[f'{col}_investigation_lift'] = (
            high_score_inv_rate / overall_inv_rate
        )
    
    # 2. 조사된 클레임에서만 사기 라벨이 관측되는가?
    # (selective labels 문제 — P1 Lakkaraju 연결)
    investigated_fraud_rate = df[df[investigation_col]==1][label_col].mean()
    not_investigated = df[df[investigation_col]==0][label_col]
    null_rate = not_investigated.isna().mean()
    results['label_coverage_gap'] = null_rate
    results['selective_label_indicator'] = null_rate > 0.5
    
    # 3. 시간에 따른 분포 이동 (Unstable Data Dependency)
    if 'claim_date' in df.columns:
        for col in model_version_cols:
            temporal_corr = df.groupby(
                pd.Grouper(key='claim_date', freq='M')
            )[col].mean()
            results[f'{col}_temporal_drift'] = temporal_corr.std()
    
    return results


def list_undeclared_consumers(pipeline_config):
    """
    §2 Undeclared Consumers 감사:
    model_score를 소비하는 모든 다운스트림 시스템 목록.
    실제 Allianz 환경에서는 파이프라인 설정/API 로그 분석 필요.
    """
    consumers = {
        'investigation_triage': True,        # 직접 피드백 루프
        'reserve_setting': None,             # 확인 필요 (숨겨진 루프?)
```

## 🇬🇧 English Summary

### 1. Problem — ML Systems as Technical Debt Generators

Using the software engineering concept of **technical debt** (Ward Cunningham, 1992), the paper argues that ML systems have a special capacity for incurring massive maintenance costs. While the ML code itself is small, the surrounding infrastructure — data collection, feature extraction, serving, configuration, monitoring — constitutes the vast majority of a production ML system (Figure 1). This infrastructure is where technical debt accumulates silently.

The paper identifies several ML-specific risk factors absent from traditional software engineering. The most directly relevant to the Allianz dissertation is **hidden feedback loops** (§4).

---

### 2. Technical Taxonomy

#### 2-1. Boundary Erosion (§2)

**Entanglement — CACE Principle (Changing Anything Changes Everything):** Changing any input signal $x_j$ in a model using features $x_1, \ldots, x_n$ may change the weights, importance, or use of all other features. No input is ever truly independent. This applies equally to full retraining and online adaptation.

**Undeclared Consumers:** If a model $m_a$'s output is accessible at runtime, other systems may silently consume it without explicit declaration. These undeclared consumers create hidden tight coupling — changes to $m_a$ affect those consumers in unintended ways, and they may **create feedback loops** (the bridge to §4).

#### 2-2. Data Dependency Debt (§3)

Code dependencies are visible to compilers and linkers. Data dependencies in ML systems have no equivalent automated tooling, making them harder to detect and more dangerous.

**Unstable data dependencies** arise when an input signal comes from another ML model that updates over time. If model output $f_t(x)$ is used as a feature by another model $g_t$, then any update to $f$ causes $g$ to behave differently — even if $g$ is not retrained. This is the precise pattern in the Allianz pipeline where `model_v1_score` may feed into downstream systems.

**Underutilised data dependencies:** Legacy features, bundled features, $\varepsilon$-features, and correlated features that provide negligible marginal benefit but increase brittleness. Detection: exhaustive leave-one-feature-out evaluations.

#### 2-3. Feedback Loops (§4) — The Core SFP Concept

This is the section most directly relevant to the dissertation.

**Direct Feedback Loops:**
> "A model may directly influence the selection of its own future training data."

The paper states this is technically the correct problem for bandit algorithms, but contextual bandit methods do not scale to the large action spaces typical in real-world ML. Mitigation: use some amount of randomisation (§4, reference [3]), or isolate certain data from being influenced.

Formalising the Allianz SFP loop in the paper's terms: the fraud model's output $f_t$ influences investigation decisions $A_t$; the investigation decisions determine which claims generate fraud labels $Y_t$; the training dataset for the next model is $D_{t+1} = g(D_t, f_t)$. The model has a **hidden data feedback loop**.

**Hidden Feedback Loops:**
Two systems influence each other indirectly through the world, even if they appear completely disjoint. The paper's stock-market example: two investment firms' prediction models influence trading activity, which influences prices, which are inputs to both models. Neither team observes the coupling directly.

In Allianz terms: the fraud model influences reserve setting; reserves influence how aggressively claims are settled; early settlement reduces investigation opportunity; fewer investigations means less fraud discovered; this changes future training data — all without any direct data connection visible in the pipeline.

#### 2-4. ML System Anti-Patterns (§5)

| Anti-Pattern | Description | Allianz Risk |
|-------------|-------------|--------------|
| **Glue Code** | Massive supporting code to connect general-purpose packages; freezes system to package-specific quirks | DoWhy + econml + LightGBM integration complexity |
| **Pipeline Jungles** | Data preparation evolves into a jungle of scrapes, joins, sampling steps with intermediate files | `generate_synthetic.py` → multiple build phases chain |
| **Dead Experimental Codepaths** | Accumulated experimental branches; Knight Capital lost $465M in 45 minutes due to obsolete codepath (§5) | Experimental fraud score variants left in production |
| **Abstraction Debt** | No widely accepted ML system abstractions — "What is the right interface for a stream, a model, or a prediction?" | Lack of standardised model versioning interface |

#### 2-5. Configuration Debt (§6)

Configuration files can exceed the size of model code. Every configuration line is a potential source of error. The paper's checklist for good configuration systems: small changes from previous configurations, hard to make manual errors, easy to see diffs, easy to assert facts automatically, easy to detect unused settings, configurations under code review.

**Allianz relevance:** The deployment windows of model v1, v2, v3 — their exact dates, thresholds, and scoring parameters — constitute configuration that must be documented to make temporal analysis in Build 00 valid.

#### 2-6. Monitoring for Feedback Loop Detection (§7)

Three monitoring signals relevant to detecting SFP loops:

- **Prediction Bias:** In a correctly functioning system, the distribution of predicted labels should equal the distribution of observed labels. If the fraud model's predicted fraud rate diverges from the observed fraud rate, this signals that the model has drifted from the data distribution it created. This is a direct operational signal of the SFP loop.
- **Action Limits:** For systems that take actions in the world (e.g., marking claims for investigation), set and enforce action limits as a sanity check. If the investigation rate suddenly changes, trigger alerts.
- **Up-stream Producer Monitoring:** Changes to data feeds upstream of the fraud model propagate silently to model behaviour. Monitor data quality SLAs at all ingestion points.

```python
# Build 00: eda_template.py
# §4 SFP Audit — identifying the feedback loop graph

def build_dependency_graph(pipeline_config: dict) -> dict:
    """
    Maps data dependencies in the Allianz fraud pipeline.
    Based on §3 'Static Analysis of Data Dependencies'.
    
    In a production system, this would be automated via 
    feature store metadata. Here we document manually.
    """
    graph = {
        # Direct feedback loop (§4 Direct Feedback Loops)
        'model_vX_score': {
            'inputs': ['amount', 'postcode_risk', 'prior_claims', 
                       'claim_type', 'product_line'],
            'outputs': ['investigation_decision'],   # action
            'feedback_path': 'investigation_decision -> fraud_label -> retrain'
        },
        # Potential hidden feedback loops (§4 Hidden Feedback Loops)
        'reserve_setting': {
            'inputs': ['model_vX_score'],            # undeclared consumer?
            'outputs': ['settlement_timeline'],
            'feedback_path': 'settlement_timeline -> investigation_opportunity -> fraud_label'
        },
        'adjuster_assignment': {
            'inputs': ['model_vX_score', 'claim_type'],
            'outputs': ['adjuster_expertise'],
            'feedback_path': 'adjuster_expertise -> investigation_quality -> fraud_label'
        }
    }
    return graph

def compute_technical_debt_score(df, model_cols, inv_col, label_col):
    """
    §9 'Measuring Debt and Paying it Off' — quantitative proxies.
    """
    debt = {}
    
    # Q1: How easily can a new algorithm be tested?
    # Proxy: fraction of claims without any model score (coverage gap)
    debt['coverage_gap'] = df[model_cols].isna().mean().mean()
    
    # Q2: Transitive closure of data dependencies  
    # Proxy: correlation between model versions (sign of tight coupling)
    if len(model_cols) >= 2:
        debt['version_coupling'] = df[model_cols].corr().values[0, 1]
    
    # Q3: Impact precision
    # Proxy: variance of investigation rate across time windows
    if 'claim_date' in df.columns:
        monthly_inv = df.groupby(
            pd.Grouper(key='claim_date', freq='M')
        )[inv_col].mean()
        debt['investigation_rate_variance'] = monthly_inv.var()
    
    # Q4: Improving one model degrades another?
    # Proxy: label coverage by model version (does v2 improve on v1's blind spots?)
    debt['label_coverage_by_version'] = {
        col: df[df[col].notna()][label_col].notna().mean()
        for col in model_cols
    }
    
    return debt
```

### 5. Limitations

- **No quantitative metrics for debt:** The paper provides checklists and heuristics but no formula for measuring the severity of a feedback loop. Quantitative severity measures require the causal inference tools from P16 (DML) and theoretical bounds from P15 (performative prediction).
- **Google-scale focus:** Many recommendations (automated feature management systems, SLA enforcement, action limits infrastructure) assume Google-scale engineering resources not available in an Allianz internship context.
- **2015 vintage:** Pre-dates large language model pipelines, federated learning, model cards, and MLOps tooling (MLflow, Weights & Biases). However, CACE and the direct/hidden feedback loop taxonomy remain valid.
- **No detection algorithm:** The paper names feedback loops as a problem and suggests partial mitigations (randomisation, bandit algorithms) but provides no detection algorithm. This gap is filled by the SFPDetector in Build 02 (`loop_detector.py`), which implements a systematic 4-step detection procedure.
- **Bandit algorithm scalability gap:** The paper correctly identifies bandit algorithms as the theoretically right tool but notes they do not scale to large action spaces. The Build 05 randomisation strategy addresses this using ε-greedy and Thompson sampling with a cost-benefit wrapper — a practical middle ground.
